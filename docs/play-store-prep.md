# Google Play 배포 준비 점검표

작성: 2026-11-09 (같은 날 갱신). **코드에서 확인한 것**과 **확인하지 못한 것**을 나눠 적었습니다.
Play 정책 수치(마감일, 요건)는 대부분 2차 자료이므로 Play Console 안내로 직접 확인해야 합니다.

## 1. 지금 저장소 상태 (코드에서 확인)
| 항목 | 상태 |
|---|---|
| applicationId / versionCode / versionName | `com.chatlearn` / 1 / 0.1 (첫 출시 버전 이름은 정해야 함) |
| compileSdk / targetSdk / minSdk | 36 / **36** / 26 |
| release 빌드 | R8 코드 축소·난독화·리소스 축소 켜짐. `keystore.properties`가 있으면 서명, 없으면 서명 없는 APK |
| 시험용 빌드 `releaseCheck` | release와 같은 R8 설정, 앱 ID `com.chatlearn.rc`(기존 앱·데이터와 분리), 디버그 키 서명 |
| CI | 단위 테스트 + release·releaseCheck 빌드 + 시험용 APK 업로드 |

| 자동 백업 | 켜짐. 규칙은 스냅샷 폴더 포함 하나뿐이고, `<include>`가 있으면 그 밖의 파일(DB, API 키 저장소)은 백업되지 않음(ManifestTest가 검사, lint가 전제로 삼음). 실기기 복원은 미검증 |
| 네트워크 목적지 | `generativelanguage.googleapis.com`(사용자 키로 직접 호출). 디버그 빌드만 평문 HTTP 허용 |
| 권한 | INTERNET, POST_NOTIFICATIONS, RECEIVE_BOOT_COMPLETED |

## 2. 한 일과 검증 수준
| 항목 | 한 일 | 검증됨 | 검증 안 됨 |
|---|---|---|---|
| targetSdk 36 | 값을 올림. Robolectric 4.14.1이 36을 지원하지 않아 단위 테스트는 SDK 35로 고정(`robolectric.properties`) | 컴파일, 단위 테스트(CI, Android 15 시뮬레이션) | **Android 16 동작 전부.** 실기기에서 `docs/device-check.md` 12번 |
| R8 | release 규칙(`app/proguard-rules.pro`) | CI에서 빌드되는지 | **릴리스 앱이 실제로 도는지**(직렬화, Room, 암호화 저장소) — 실기기에서 `docs/device-check.md`로 |
| 서명 | 키 정보를 저장소 밖에서 읽음 | 서명 없는 빌드 | 업로드 키로 서명한 빌드 |

## 3. 사용자가 해야 하는 일
1. **실기기 확인**: `docs/device-check.md` 절차로 releaseCheck APK 시험. 특히 2번(키 저장·연결), 9번(백업 직렬화).
2. **업로드 키 만들기와 보관**: 키스토어는 저장소에 넣지 않습니다(`.gitignore`에 추가함). 분실하면 업데이트가 어려워지니 안전한 곳에 복사본을 두세요. Play 앱 서명을 쓰면 업로드 키만 관리합니다.
3. **방침 공개**: ① 이 변경을 `main`에 병합 ② 저장소 Settings > Pages > Branch `main`, 폴더 `/docs` ③ 공개 주소(예: `https://sikomar00.github.io/langLearningChat/privacy-policy`)를 Play Console에 입력. 주소가 열리는지 직접 확인해야 합니다(테마 렌더링은 제가 확인하지 못했습니다).
4. **게시 전에 대조할 문장**: 방침 3항과 앱 설정 > AI 탭의 "무료 이용 시 입력이 서비스 개선에 쓰이고 사람이 검토할 수 있다"는 문구는 tech-radar-agent ADR-0004(2026-11-05)의 약관 확인 기록에 근거합니다. 현행 Google 약관과 맞는지 확인해 주세요.
5. **Play Console 입력**: 데이터 보안 양식, 콘텐츠 등급, 대상 연령(방침 8항은 "아동 대상 아님"), 스토어 등록정보 자산(아이콘 512px, 기능 그래픽, 스크린샷).
6. **심사용 접근 정보**: 앱이 API 키 없이는 AI 기능을 못 쓰므로, 심사자용 **임시 키**(한도 제한, 폐기 가능)를 앱 액세스 안내에 제공해야 할 수 있습니다.

## 4. 확인하지 못한 것 (Play Console 안내로 확인)
- 보도 기준 targetSdk 36 요구(2026-08-31)의 정확한 적용 범위.
- 생성형 AI 앱에 요구되는 **앱 안 신고·피드백 기능** 여부와 이 앱이 해당하는지.
- 신규 개인 개발자 계정의 **비공개 테스트 요건**(테스터 수, 기간)의 현재 기준.
- 데이터 보안 양식에서 "사용자 입력 글을 Google Gemini API로 전송"을 어떻게 분류하는지. (공식 정책 문서는 서드파티 AI 연동도 공개·동의 대상이라고 함.)

## 5. 제품 측면 (심사와 별개로 채택률에 영향)
- **API 키를 직접 발급해야 하는 첫 사용 장벽**이 가장 큼. 안내 3단계를 넣었지만, 일반 사용자가 끝낼지는 모름.
  배포 전에 주변 몇 명에게 첫 실행을 시켜 보고 어디서 멈추는지 관찰할 것.
- 호스팅 키 방식(운영자가 키를 대고 사용자는 키 없이 사용)은 비용, 남용 방지, 개인정보 처리 책임이 모두 운영자에게 생김. 이 문서의 범위 밖.

## 6. 데이터 보안 양식 초안 (확인 필요)
| 질문 | 초안 답 | 근거 |
|---|---|---|
| 운영자가 데이터를 수집하는가 | 아니오 (서버 없음) | 네트워크 호출은 사용자 키로 Google에 직접 |
| 제3자와 공유하는가 | **예**: 사용자가 입력한 글을 Google(Gemini API)에 전송 | 코드: `GeminiAiService` |
| 공유 데이터 유형 | 사용자 생성 콘텐츠(메시지/문장) | 위와 같음 |
| 전송 중 암호화 | 예 (HTTPS) | `GEMINI_BASE_URL`이 https |
| 삭제 요청 수단 | 앱 삭제·앱 안 삭제 / Google 계정 | 방침 7항 |
| 선택 사항인가 | 예: AI 기능을 쓸 때만 전송 | 키를 넣지 않으면 전송 없음 |
